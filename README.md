# Babylon Standalone HTML Engine

A Babylon.js project setup that compiles into a **standalone HTML application** that does not require hosting or a local web server.

This is especially useful for environments such as **school Chromebooks**, where running a local development server may not be practical.

The project also includes an asset pipeline that converts external assets such as `.glb` models and textures into JavaScript-accessible Base64 data URLs, allowing them to work without running into browser CORS restrictions.

### `types/global.d.ts`

Contains global TypeScript type declarations used by the asset system.

In particular, generated Base64 assets are typed as `Base64String`.

This is mostly a semantic type indicating that the string contains a Base64/data URL representation of an asset.

# How the Asset System Works

Normally, browser security prevents a standalone HTML file from freely loading nearby files.

For example, suppose you have:

```text
index.html
character.glb
```

You might expect this to work:

```ts
fetch("./character.glb");
```

However, when opening `index.html` directly through a `file://` URL, browsers will generally block this because of CORS and local-file security restrictions.

The asset pipeline avoids this problem by embedding the asset as a Base64 data URL.

---

## Example

Suppose you add:

```text
assets/models/character.glb
```

During the asset build step, the file is converted into something similar to:

```js
Base64Assets["models-character.glb.js"] = "data:model/gltf-binary;base64,...";
```

A generated JavaScript file such as:

```text
models-character.glb.js
```

contains the encoded asset.

That file can then be included directly in the HTML:

```html
<script src="models-character.glb.js"></script>
```

Because the data is now loaded as JavaScript rather than fetched from the filesystem, the browser does not need to make a separate request for `character.glb`.

---

# Accessing Assets Through `R`

The asset build process automatically generates an `R` class.

For example:

```text
assets/models/character.glb
```

can be accessed through something similar to:

```ts
R.models.characterglb();
```

Internally, this returns the generated Base64 asset string.

Conceptually:

```ts
R.models.characterglb();
```

returns:

```ts
Base64Assets["models-character.glb.js"];
```

This means you generally do not need to reference generated asset filenames directly.

---

# Loading a GLB in Babylon.js

Babylon.js can load Base64 data URLs directly.

For example:

```ts
const container = await LoadAssetContainerAsync(R.models.characterglb(), scene);
```

No HTTP server is required.

No `fetch()` request to the original `.glb` file is required either.

---

# Converting an Asset Back Into a File

If you need a `Blob` or `File` object instead of passing the Base64 URL directly to Babylon.js, you can still use `fetch()` on the generated data URL:

```ts
const blob = await fetch(R.models.characterglb()).then((res) => res.blob());

const file = new File([blob], "character.glb", {
  type: "model/gltf-binary",
});
```

You can then use the resulting `File` however you want.

For normal Babylon.js asset loading, however, this is usually unnecessary because Babylon already accepts data URLs directly.

# Why This Exists

A typical Babylon.js project expects assets to be served over HTTP:

```text
Browser
   ↓
Local/Web Server
   ↓
HTML + JavaScript + Models + Textures
```

This project instead packages assets so the final project can work more like:

```text
Standalone Files
   ↓
Open index.html
   ↓
Game Runs
```

This makes the project useful for:

- School Chromebooks
- Restricted computers
- Offline demos
- USB-distributed projects
- Small game prototypes
- Environments where running a local server is inconvenient

The goal is to make a Babylon.js project as portable as possible while still supporting models, textures, and other external assets.
